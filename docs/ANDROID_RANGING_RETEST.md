# Body Finder – RuView: Android BLE/Ranging Retest

> Target build: `0.2.0-experimental.4`  
> Protocol: `2`  
> Purpose: verify the fixes found during the first physical test with Pixel 10 Pro, Pixel 7 Pro and Lenovo TB-J606L before resuming human-presence tests.  
> Safety: experimental RF software, **not validated for rescue use**.

---

## 1. Use one prerelease only

Download every Android artifact from the same newest `dev-*` prerelease generated by the stabilization implementation.

Required for this retest:

```text
body-finder-ruview-universal.apk
body-finder-ruview-legacy-minsdk21.apk
ANDROID_RANGING_RETEST.md
release-manifest.json
SHA256SUMS
```

Use the universal APK on Pixel 10 Pro, Pixel 7 Pro and Lenovo TB-J606L first. Use the legacy APK only if the Lenovo cannot install/run the universal APK.

Do not mix APKs from different releases.

## 2. Verify checksums

Linux/WSL:

```bash
sha256sum --check SHA256SUMS
```

Windows PowerShell, for each APK if GNU `sha256sum` is unavailable:

```powershell
Get-FileHash .\body-finder-ruview-universal.apk -Algorithm SHA256
```

Compare with the corresponding line in `SHA256SUMS`.

## 3. Device preparation

All devices:

```text
Wi-Fi: ON
Same Wi-Fi/LAN: YES
Bluetooth: ON
Body Finder app: foreground
Battery saver: OFF for this short test if practical
Manual X/Y/Z: NEVER enter any coordinates
Human-presence calibration: DO NOT run yet
```

### Lenovo TB-J606L / Android 11 API30

Also ensure:

```text
Location service: ON
App location permission: ALLOW while using app
```

Android <=11 may gate BLE scan results behind location state even when the BLE hardware itself is available.

### Pixel 7 Pro / API34

Grant when requested:

```text
Nearby devices / Bluetooth scan
Bluetooth connect
Bluetooth advertise
Nearby Wi-Fi devices
Location if requested by the OS/build
```

### Pixel 10 Pro / API36+

Grant the same permissions plus `RANGING` if Android asks for it.

The system Ranging API is optional. A failure or close in that API is **not** a failure by itself if the independent Body Finder BLE-RSSI fallback produces fresh ranges.

```bash
adb -s PIXEL10_SERIAL install -r body-finder-ruview-universal.apk
```

# TEST T1 — Pixel 10 Pro + Pixel 7 Pro

This is the first blocking acceptance test.

## Placement

Place the two Pixel phones approximately 1–3 m apart, stationary, with no need to measure exact coordinates yet.

## Procedure

1. Close/stop Body Finder on Lenovo.
2. Open Body Finder on Pixel 10 Pro and Pixel 7 Pro.
3. Keep both apps in foreground.
4. Wait 60 seconds.
5. Open Expert on each phone.
6. Inspect `BLE / ranging diagnostics`.

## Expected acquisition chain

For the remote peer, expect progression similar to:

```text
BLE_IDENTITY_KNOWN
        ↓
BLE_IDENTITY_SEEN / ADDRESS_BOUND
        ↓
SAMPLES_ACQUIRING
        ↓
RANGE_READY
```

Exact labels may differ slightly, but the exported fields must make the stage unambiguous.

## Required evidence

At least one direction must show:

```text
body_finder_scan_results > 0
body_finder_scan_results_for_identity > 0
sample_count_5s >= 3
last_sample_age_ms <= 5000
fallback_range_ready = true
```

The app must then expose a real `PairwiseRangeObservation` with either:

```text
technology = BLE_RSSI
```

or, if Android API36+ actually produced a fresh system distance:

```text
technology = ANDROID_RANGING_BLE_RSSI
```

The observation must include:

```text
observer_node_id
peer_node_id
distance_m
distance_sigma_m
rssi_dbm
monotonic_ns
quality
source_detail
```

## Geometry pass condition

With exactly two nodes and at least one valid pairwise distance:

```text
nodes = 2
valid_edge_pairs >= 1
GEOMETRY 1D
positions = 2
```

The app must **not** show 2D with only two nodes.

## If T1 fails

Do not proceed to T2. Export JSON from both phones immediately and save screenshots of:

```text
BLE / ranging diagnostics
Fabric diagnostics
Range observations
Graph diagnostics
Capabilities
```

The important blocker fields are:

```text
scan_state
advertise_state
body_finder_scan_results
binding_state
sample_count_5s
last_sample_age_ms
blocking_reason
system_ranging.state
system_ranging.last_close_reason
fabric peer last_seen_age_ms
```

# TEST T2 — Add Lenovo as third node

Run only after T1 passes.

## Placement

Arrange the three phones as a clearly non-collinear triangle, for example:

```text
Pixel 10 ---------------- Pixel 7
     \                      /
      \                    /
       \                  /
             Lenovo
```

Keep them stationary.

Do **not** enter coordinates into Body Finder.

## Procedure

1. Keep both Pixel apps running.
2. Open Body Finder on Lenovo.
3. Wait 90 seconds.
4. Confirm all three nodes are visible.
5. Inspect Expert on all three.

## BLE requirements

The Lenovo must not show the previous permission failure.

For distance-only ranging, the desired complete graph is:

```text
Pixel10 ↔ Pixel7
Pixel10 ↔ Lenovo
Pixel7  ↔ Lenovo
```

That is three unique pairwise distance edges.

## Geometry pass condition

For a non-collinear triangle with three valid distance constraints:

```text
nodes = 3
valid_edge_pairs = 3
GEOMETRY 2D or GEOMETRY DEGRADED with 3 solved positions
positions = 3
```

`GEOMETRY DEGRADED` is acceptable only if Expert explains a real uncertainty/conditioning issue. Missing constraints must never be hidden.

If there are only two distance edges, `1D/INSUFFICIENT/DEGRADED` is correct; do not treat that as a solver defect.

# TEST T4 — Five-minute stability

Run only after T2 passes.

Keep all three phones stationary for five minutes.

Inspect/export:

```text
peer_expire_count
peer last_seen_age_ms
body_finder_scan_results
address_rebind_count
sample_count_5s
last_sample_age_ms
range observations
geometry state/revision
```

Desired lab behavior:

```text
peer_expire_count = 0 during a stable foreground/LAN test
fresh range available for most of the interval
no unexplained peer disappearance
no fabricated edge when samples become stale
```

Address rebinds are not automatically failures; Android may randomize BLE endpoints. The persistent `node_id` must remain stable.

# TEST T5 — API36+ failure/fallback truth on Pixel 10 Pro

On Pixel 10, inspect:

```text
ble_diagnostics.system_ranging
```

Possible system states include:

```text
READY_NO_BOUND_PEER
STARTING
ACTIVE_NO_RESULT
ACTIVE_RESULT
OPEN_FAILED
CLOSED
BACKOFF
FAILED
```

If system ranging closes/fails, verify the app still emits `BLE_RSSI` fallback when fresh BLE advertisement samples exist.

A system state such as `CLOSED reason=<n>` is acceptable if:

```text
fallback_range_ready = true
range_observations contains BLE_RSSI
```

No symbolic interpretation of an unknown numeric Android reason should be invented.

# 7. Stop/go criteria for the wider test campaign

Do not resume empty-scene/person/LOS/wall tests until all of these are true:

```text
[ ] Lenovo legacy Bluetooth permission failure gone
[ ] Pixel10 + Pixel7 produce >=1 real pairwise range edge
[ ] two-node geometry reaches 1D
[ ] three nodes produce all distance constraints required for a defensible 2D solution
[ ] no manual coordinates used
[ ] capability state matches observed evidence
[ ] API36 failure does not disable fallback
[ ] UDP peer loss, if any, is explained by diagnostics
```

Only after those pass should the larger `TESTING_AUTOGEOMETRY_RELEASE.md` protocol continue with empty scene, LOS human presence, movement, wall, Ubuntu, Windows and WSL.

---

# 8. What constitutes a valid failure

A failure is useful if the diagnostics identify its stage. Examples:

```text
ADVERTISEMENT_NOT_SEEN
INSUFFICIENT_SAMPLES
STALE_SAMPLES
PERMISSION_REQUIRED
BLE scan failed code=<n>
advertise failed code=<n>
API36 CLOSED reason=<n>
peer expired after <age> ms
```

Do not retry blindly before exporting the JSON. The purpose of this stabilization build is that a single failed run contains enough evidence to locate the failing stage.
